# Union-Find Context Compaction: Experiment Results

**Date:** 2026-03-18
**Author:** June Kim
**Classification:** Exploratory benchmark validation
**Preregistered:** Yes (before implementation)

---

## Summary

Union-find context compaction does not improve factual recall over aider's recursive summarization. The two systems are quality-equivalent on a 136-observation paired benchmark. Union-find passes on engineering metrics (sub-millisecond synchronous latency, 1.14x cost) but misses its primary hypothesis (recall improvement).

Per the preregistered decision rules: H1 miss, H2a pass, H3 pass maps to "Document; note aider's stronger baseline may close the gap." No PR opened.

---

## Background

Aider compresses chat history via hierarchical recursive summarization: split messages at the half-budget token boundary, summarize the older half, recurse if still too large (max depth 4). This is lossy and irreversible, but it works. The algorithm doesn't respect topic boundaries -- it splits wherever the token count happens to land.

Union-find context compaction is a different approach. Messages graduate from a "hot zone" into a forest of topic-coherent clusters, grouped by TF-IDF similarity. Each cluster gets its own summary. When clusters grow similar, they merge. The hypothesis was that topic-coherent summaries would retain more factual detail than arbitrary token-boundary splits.

This architecture was ported from gemini-cli, where it showed a +8.3pp recall trend (not significant at p=0.136 with 96 observations). The aider port was an opportunity to test with more power (192 target observations) against a stronger baseline (recursive vs flat).

## Method

### Conversations
17 conversations generated from real GitHub issues across 7 repositories (flask, fastapi, pytorch, vscode, requests, httpx, cpython). Each conversation was expanded to 200 messages simulating a developer-assistant exchange about the issue. Target was 24, but django returned no qualifying issues and some repos had fewer than 4.

### Questions
8 factual recall questions per conversation (136 total), generated by Gemini 3.1 Flash Lite. Questions span early/mid/late regions of the conversation and cover at least 3 categories (filenames, function names, libraries, error messages, decisions, configuration, API endpoints, test cases). Questions were frozen before running either system.

### Systems
Both systems compressed the same 200-message conversations using the same model (Gemini 3.1 Flash Lite):
- **Union-find:** `ChatSummaryUF` -- topic-coherent clusters, incremental feeding, TF-IDF similarity
- **Recursive:** `ChatSummary` -- aider's existing hierarchical split-and-summarize

### Judge
Blinded LLM-as-judge (GPT-5.4 via `codex exec`). The judge saw the compressed history and a question, not which system produced it. A/B assignment randomized per conversation (deterministic via SHA256). Binary scoring: CORRECT or INCORRECT.

### Analysis
- **H1 (Recall):** McNemar's test with continuity correction on 136 paired binary outcomes. Sensitivity: conversation-level sign test.
- **H2 (Latency):** p50/p90/p95/max for append, render (synchronous), and resolveDirty (deferred LLM work).
- **H3 (Cost):** Total token ratio (union-find / recursive).

### Futility
Checked at conversation 12: McNemar's b=2, c=1, p=1.000, cost=1.07x. Effect too small to be significant but not definitively null (only 3 discordant pairs). Experiment continued.

## Results

### H1: Recall -- MISS

| System | Correct | Total | Rate |
|--------|---------|-------|------|
| Union-Find | 54 | 136 | 39.7% |
| Recursive | 56 | 136 | 41.2% |

**Effect:** -1.5pp (UF slightly worse)
**McNemar's chi2:** 1.33, **p = 0.248**
**Discordant pairs:** b=3 (UF correct, Rec wrong), c=0 (Rec correct, UF wrong)

The striking finding is how few discordant pairs there are. Out of 136 questions, the two systems disagreed on only 3. They get the same questions right and the same questions wrong.

**Sign test (sensitivity):** 5 UF wins, 7 Rec wins, 5 ties (p = 0.774). No signal at the conversation level either.

### H2: Latency -- PASS

**H2a: Append + Render (target: p95 < 100ms)**

| Operation | p50 | p90 | p95 | max |
|-----------|-----|-----|-----|-----|
| Append | 0.03ms | 0.06ms | 0.08ms | 0.19ms |
| Render | 0.01ms | 0.02ms | 0.02ms | 0.03ms |

Both operations are three orders of magnitude under the target. These are pure data structure operations with no LLM calls.

**H2b: ResolveDirty (informational)**

| p50 | p90 | p95 | max |
|-----|-----|-----|-----|
| 1,524ms | 2,476ms | 4,151ms | 8,571ms |

This is where cluster summaries are generated via LLM calls. In aider's threading model, this runs in a background thread -- the user doesn't wait unless their next message arrives before `resolveDirty` finishes.

### H3: Cost -- PASS

| System | Total Tokens |
|--------|-------------|
| Union-Find | 382,348 |
| Recursive | 335,232 |

**Ratio:** 1.14x (target: <= 2x)

Union-find uses 14% more tokens. The extra cost comes from per-cluster summarization calls (many small) vs recursive's fewer but larger calls. Well within the 2x budget.

## Interpretation

### Why no recall difference?

Three candidate explanations:

**1. The summarization model is the bottleneck, not the chunking strategy.** Both systems scored ~40% overall. That's low enough to suggest the LLM (Gemini 3.1 Flash Lite) struggles to produce informative summaries regardless of how the input is organized. A stronger model might show a difference between topic-coherent and token-boundary chunking, or it might not.

**2. Aider's recursive baseline is stronger than gemini-cli's flat baseline.** The gemini-cli experiment compared union-find against flat single-snapshot summarization (compress everything in one call). Aider's recursive approach preserves recent messages verbatim at each recursion level, giving it better recency preservation. The union-find architecture was designed to beat a weaker opponent.

**3. The recall questions may not discriminate.** Only 3 discordant pairs out of 136 observations. Either the questions are too easy (both systems get them right) or too hard (both fail), with very little in the middle where chunking strategy matters. A better question set might target the specific advantage of topic-coherent compression -- details from the middle of the conversation that belong to a coherent topic thread.

### What the numbers do say

The two systems are quality-equivalent. This is itself a finding: a structurally different compression architecture produces indistinguishable output quality. The choice between recursive and union-find is an engineering choice (code complexity, extensibility, cost), not a quality choice.

Union-find's engineering story is solid. Sub-millisecond synchronous operations mean the user never waits for data structure work. The 1.14x cost overhead is modest. The architecture supports future features (expand clusters, search by topic) that recursive summarization can't offer. But none of that matters if the quality bar is the same.

### What we'd do differently

1. **Use a stronger summarization model.** Flash Lite may be too weak to show a difference. The architectural advantage of topic-coherent chunking might only matter when the summarizer is good enough to exploit it.
2. **Target 24 conversations.** We got 17 due to repo availability issues. More data might surface a small effect, though the near-zero discordant pair count (3/136) suggests the effect simply isn't there.
3. **Design discriminating questions.** Questions that specifically target cross-topic coherence -- "what was the relationship between the authentication refactor and the database migration?" -- rather than single-fact recall.

---

## Decision

Per preregistered decision rules:

> H1 ❌ H2a ✅ H3 ✅ → "Document; note aider's stronger baseline may close the gap"

The tuning policy allows 2 parameter changes before accepting the H1 result. Given only 3 discordant pairs, tuning merge threshold or max clusters is unlikely to move the needle. The signal isn't "effect too small to detect" -- it's "the systems produce nearly identical output."

**Recommendation:** Do not open a PR on aider. The union-find architecture is not worth the added complexity without a recall advantage. Document the experiment, the null result, and the lessons learned.

---

## Lessons

1. **Stronger baselines close gaps.** An approach that beats a weak system may tie a strong one. Always benchmark against the actual target, not a strawman.

2. **Preregistration works.** Classifying this as exploratory from the start meant the null result was a legitimate finding, not a failure to reclassify. The futility rules prevented premature stopping (the experiment continued past 12 conversations and the later data confirmed the null).

3. **Discordant pairs matter more than aggregate scores.** UF 39.7% vs Rec 41.2% looks close but uninformative. The fact that only 3 out of 136 pairs were discordant tells the real story: these systems are producing functionally identical output.

4. **Engineering metrics are necessary but not sufficient.** Sub-millisecond latency and 1.14x cost are good numbers, but they don't justify shipping additional complexity without a quality win.

5. **Null results are results.** "Union-find compaction does not improve recall over recursive summarization on this benchmark" is a useful finding. It saves future developers from pursuing this approach for quality reasons, while leaving the door open for engineering reasons (extensibility, future features) if those become valuable.
